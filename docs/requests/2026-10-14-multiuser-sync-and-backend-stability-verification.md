# 2026-10-14 多人在线实时同步与后台接口稳定性验证需求

## 需求背景
UI 重构完成后，需要全面验证并确保后端与全栈交互（UX）能够完美匹配实际运营需求，主要包含两大核心关切：

1. **多人协同与实时同步保障**：
   - 多人（多个教练、多名游泳队员）同时在线或访问网站时，数据同步机制是否通畅？
   - 教练发布训练计划、修改内容、发送通知后，队员端无论是主动刷新还是自动轮询同步，是否能够即时无缝拉取到最新数据？
   - 队员提交的训练反馈、出勤自查、伤病记录，教练端是否能即刻获知？

2. **接口与网络稳定性**：
   - API 数据链路与数据库连接（Neon PostgreSQL / Cloudflare Edge / WebSocket / Polling）是否健壮？
   - 是否存在因网络抖动、并发请求、缓存穿透或内存泄漏导致系统“用着用着就崩掉”的风险？
   - 错误处理机制（Fallback、重试、Toast 通知、脱机容灾）是否健全清晰？

## 验证与审查范围
1. `lib/store.ts`：本地状态、跨标签页同步（BroadcastChannel / localStorage）、自动定时同步（`syncInterval`）、乐观更新与回滚。
2. `app/api/sync/route.ts`：增量同步与全量同步逻辑、版本时间戳（`updatedAt` / `lastSync`）。
3. `lib/api-client.ts`：网络请求重试、超时控制、网络异常恢复。
4. `components/dashboard/RefreshButton.tsx`：手动同步触发与状态指示。
5. 关键业务路径（训练发布 -> 队员查看，队员反馈 -> 教练审阅）。

## 验证结论与系统保障措施

### 1. 多人同时在线与实时同步验证结论
- **三重同步保障**：
  1. **自动轮询（20秒增量轮询）**：`lib/store/sync-engine.ts` 设置 `POLL_INTERVAL_MS = 20000`，保持打开页面即可静默刷新最新数据。
  2. **页面可见性与焦点即时触发（Focus/Visibility Sync）**：队员或教练只要切换窗口、解锁手机或切回页面，立即瞬时触发同步。
  3. **主动刷新与零白屏单点同步**：
     - 普通浏览器刷新（`Cmd+R` / `F5` / 手机下拉）：首屏自动执行 `loadData()`，直接拉取数据库最新发布内容。
     - 教练端配备 `<RefreshButton />`，队员端顶部新增一键手动同步按钮 `<RefreshCw>`，支持无需白屏刷新的即时静默同步。
- **并发与权限裁剪（Role Scoping）**：
  - 针对 70+ 名队员高并发访问，`app/api/sync/route.ts` 会自动根据身份裁剪数据负荷，队员仅拉取其个人关联数据与近期计划，剔除过期冗余多媒体，保证高并发下低延迟响应。
- **乐观更新锁（Mutation Guard）**：
  - 教练发布内容或队员提交数据后，系统启动 15 秒锁定，防止被旧的轮询结果覆盖，并在服务端写入完成后平滑合入。

### 2. 接口与网络稳定性验证结论
- **无状态 HTTP 数据库连接池（Neon Serverless）**：
  - `lib/db-pool.ts` 采用单例 `getNeon()`，配置 `pgbouncer=true&connection_limit=50`，基于 HTTP/WebSocket 协议，杜绝高并发时的 TCP 连接耗尽和连接泄漏崩溃。
- **冷启动智能预热（Cold-Start Warmup Loop）**：
  - `app/api/sync/route.ts` 内置 3 次重试预热机制，配合客户端 45 秒自适应超时和指数退避重试，防止数据库休眠导致的 500 崩溃。
- **脱机容灾与本地快照双轨机制（Offline Fallback）**：
  - 所有核心数据均通过 `lib/store/persist-layer.ts` 本地存储缓存；遇到突发网络中断时，页面正常呈现本地数据并进入离线保护模式，每 30 秒后台自动重试恢复。
- **全栈错误边界与保护网**：
  - 后端经由 `lib/api-handler.ts` 的统一异常捕获包装，杜绝进程挂死；前端具备 `app/error.tsx` 全局错误兜底，绝不会“用着用着就彻底崩掉或白屏锁死”。
